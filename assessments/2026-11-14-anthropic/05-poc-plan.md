## 5. POC plan (pre-registered, plan only — dated Sat Nov 14, 2026)

- **Question the pilot settles:** On this team's real ticket mix, does the two-leg chain (Claude Haiku 5.5 summarizing, Claude Sonnet 5.5 drafting) produce reply drafts an agent can send with only minor edits at the pre-set rate, with zero hard-constraint failures, at the worksheet's cost (§4)?
- **Setup:** Models as inventoried in §1: Claude Haiku 5.5 (summarizer) and Claude Sonnet 5.5 (drafter) on the standard Messages API; the Batch API is excluded (decision 1, below). No dated snapshot exists for either model (Dimension 1), so the version record is the model ID plus this plan's date, and any behavior-affecting release-notes entry reopens the evaluation under §4.3 before results are read. Scope: one support queue. Evaluation runs on closed historical tickets with direct identifiers redacted by the customer's own tooling before any API call, under standard documented terms (decision 2, below). Drafts are approved by the handling agent in the ticketing system; approve-before-send is enforced there, never in the model call. The live pilot, distinct from this POC, is gated on a written zero-retention arrangement with the vendor and a completed privacy impact assessment (§4 handoff).
- **Decisions recorded Sat Nov 14, 2026 (Paulo):** (1) Standard API on both legs; Batch stays excluded — its saving on the summarizer leg is about $0.07/day, and its 29-day retention and ZDR ineligibility break the intake's hard guarantee. (2) POC data as in Setup; the live pilot is gated on written ZDR plus the privacy impact assessment. (3) Thresholds as set in the criteria below.
- **Success criteria (set in advance; values set by Paulo, Sat Nov 14, 2026):**
  - Draft quality: share of drafts sent with only minor edits at or above **85%** — 'edit rather than rewrite,' measured by the blind review below. Baseline for comparison: today agents write every reply from scratch, so the comparison measure is median handling minutes per ticket on the same queue, taken from ticketing-system timestamps for the sampled tickets' original handling.
  - Hard constraints: zero drafts containing another customer's details; zero sends without human approval; zero retention or training-use violations.
- **Evaluation rubric:** Each sampled ticket is graded from the review record on three points: the summary's faithfulness to the ticket (no invented facts, no dropped facts that change the answer), the draft's edit kind (send as-is / minor edits / major edit / rewrite), and hard-constraint compliance. Judged by **blind human review of a random sample**: reviewers see the ticket and the draft, never the vendor's materials and never any AI pre-judgment (Issue 029: a confident note flips verdicts).
- **Sample size:** 300 closed tickets, drawn at random from the scoped queue's recent closed volume. One sample serves both measures: hard constraints sized by the rule of three: about 300 tickets with zero failures supports roughly a 1% upper bound (3/N). Quality share on the same 300 carries a margin of about ±4 points around 85%.
- **Go threshold:** Draft quality at or above 85% AND zero hard-constraint failures in the 300 → proceed to the gated pilot track (written ZDR arrangement + privacy impact assessment, §4). · **No-go threshold:** Draft quality below 70%, OR any hard-constraint failure → no pilot; the failure is worked as a change event under §4.3 before any retest. Between 70% and 85% with zero hard-constraint failures: remediate (prompt, context, or model-leg changes) and re-run the quality sample once before a pilot decision.
- **Status:** PLAN ONLY. Not run. If run later, it runs through the harness and this plan is the registration it is judged against.
